## 복구 방식

`continue-watch.cjs`는 다음 실행 요청을 최대 3회로 제한한다. 5xx 또는 알려진
응답 소실 오류가 발생하면 2초, 5초, 10초를 순서대로 기다리면서 실행을 재조회한다.
재조회에서 다음 세션이 확인되면 POST를 반복하지 않는다. 마지막 요청 실패 후에도
동일한 재조회를 수행한다. 조회 API의 일시 오류는 최대 2회(2초, 5초) 재시도하며,
조회가 끝내 실패하면 추가 POST 없이 실패를 보고한다.

기본 브랜치의 동일한 `watch-loop` 실행만 대상으로 한다. 기존 대기 실행뿐 아니라
다른 실행의 `in_progress`도 중복 방지에 포함한다. 최초 조회 이후 새로 나타난 실행은
이미 완료되었어도 요청 수락의 근거로 사용한다. 최초 조회 때 존재했던 완료 실행,
현재 실행, 진단 모드 및 다른 브랜치 실행은 복구 근거로 사용하지 않는다.
실행 목록은 페이지를 끝까지 조회한다.

재요청 전 workflow 활성 상태를 다시 확인한다. 4xx와 분류되지 않은 오류는
재시도하지 않는다. 기본 브랜치/공개 저장소 조건과 정확한 상태 캐시 확인을 유지한다.
workflow의 `WATCHER_PAUSED`, 취소 여부, 세션 완료 조건, 캐시 저장/복원 방식,
감시 주기와 Discord 전송 코드는 변경하지 않는다. 운영 캐시를 삭제하거나
초기화하거나 실제 감시 workflow를 수동 실행하지 않는다.

## 검증과 한계

Node 테스트는 GitHub API와 대기 시간을 모두 대체한다. HTTP 500/502/503/504,
응답 소실 후 지연된 실행 노출, 실행 중/완료 상태, 최종 시도 후 실행 확인,
재시도 소진, 조회 실패, workflow 비활성화, 페이지 경계와 기존 보호 조건을 검증한다.
Discord 발송은 하지 않는다.

GitHub dispatch API에는 이 코드에서 사용할 멱등성 키가 없다. 재조회 대기 시간
이후에도 실행이 목록에 나타나지 않으면 중복 요청 가능성을 완전히 배제할 수 없다.
이 구현은 제한된 재조회로 위험을 줄이며, GitHub가 장기간 장애 상태일 때는 실패를
명시하고 기존 예약 실행을 복구 수단으로 유지한다.
